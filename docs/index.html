Create your configuration

Nouli reads ~/.nouli/config.toml. Your first evaluation creates a barebones file if it is missing, then asks you to define a provider. Add a provider using the examples below.

To scaffold the file, run this example once. Until you add a provider, it returns providers_required with the configuration path.

Your shell
nouli \
  --state "Repair costs 120; replacement costs 300." \
  --questions '[{"id":"repair","prompt":"Should I repair it?","answer_space":{"type":"noul"}}]'

Use --config /path/to/config.toml for another file. An explicitly selected file must already exist.

Configure a provider

For a new config, replace the scaffold with one complete example below. Set default_provider to the provider name and default_model to a compatible model. Each provider is defined once, even when you use several models.

~/.nouli/config.toml
default_provider = "jev"
default_model = "jev-latest"
output = "auto"

[providers.jev]
protocol = "typesafe"
base_url = "https://api.typesafe.ai"
api_key_env = "TYPESAFE_API_KEY"

Use a Jev model available to your TypeSafe account.

.env
TYPESAFE_API_KEY="your-api-key"
Put the environment-variable name in api_key_env. Set its value in your shell, secret manager, or local .env file. Keep API keys out of configuration files and request files.

Load credentials from .env

Save the credential example above in .env in the directory where you run Nouli. Nouli loads it automatically for decisions and workflow execution, including resume. It does not search parent directories or your config directory. Exported shell values take precedence over the file.

Use --env-file FILE to select another file, such as nouli --env-file .env.test --input request.json. Relative paths start in the current directory. An explicit file replaces the automatic .env.

If your variable is named TYPESAFE_TOKEN, set api_key_env = "TYPESAFE_TOKEN" in your provider definition. Names must match. Env files support comments, quoted values, and optional export prefixes.

A missing automatic .env is fine. Missing explicit files, unreadable files, or malformed files stop execution, even when a key is exported. Help and read-only inspection do not load env files. Keep .env out of version control.

Place default_provider, default_model, and output before the first [providers.NAME] section. When adding another provider, add its section without repeating those top-level settings.

Choose a model

Use --model MODEL_ID to select another model for a call. To switch services too, pass --provider NAME --model MODEL_ID. The provider and model are selected independently; changing the provider does not choose a different model for you.

Explicit CLI choices take precedence over request settings, session defaults, and configuration defaults. Workflow nodes can select their own provider and model. A one-call override does not change your session defaults.

Choose a context budget

For a custom endpoint, local service, or unrecognized model, add limits under [providers.NAME.models."MODEL_ID"]. Set context_budget_tokens or context_window_tokens to a capacity that service supports. Each model has its own settings. A known model can use its recognized limit; you can also supply a budget with --context-budget TOKENS.

reserved_output_tokens reserves part of that budget for the response. Token counts shown as estimates are approximate; the provider may reject an input that is too large.

For example, after defining a local provider, you can give two served models different limits. Replace the model names and capacities with values supported by your service:

Per-model settings
[providers.local.models."model-a"]
context_window_tokens = 8192
context_budget_tokens = 4096
reserved_output_tokens = 128

[providers.local.models."model-b"]
context_window_tokens = 32768
context_budget_tokens = 16384
reserved_output_tokens = 256

Then select either model with --provider local --model model-a or --provider local --model model-b. Model entries are optional settings, not a list of allowed models. You can select another supported model without an entry; an unrecognized model still needs an explicit budget.

Supply the facts and the question

--state accepts plain text. --questions accepts a JSON question list. The short forms are -s and -q; use one hyphen for -q.

After configuring a provider, run the example above again with your own facts and question.

You can repeat --state to supply more facts. A question needs an ID, a prompt, and an answer_space.

Choice

Provide options with IDs and descriptions. The answer identifies a selected option and its probability.

Noul

Ask a yes/no question. The answer is the probability of yes, between 0 and 1.

Score

Provide ordered levels. The answer is an expected level index and can be fractional.

Use a request file

Save this example as request.json. Edit its state, questions, and answer spaces for your decision. Choice supports 2-255 options; score supports 2-10 levels.

request.json
{
  "state": [{"type": "text", "text": "The train takes 4 hours; the flight takes 2 hours."}],
  "questions": [
    {
      "id": "route",
      "prompt": "Which route should I take?",
      "answer_space": {
        "type": "choice",
        "options": [
          {"id": "train", "description": "Take the train"},
          {"id": "flight", "description": "Take the flight"}
        ]
      }
    },
    {
      "id": "on_time",
      "prompt": "Will I arrive on time?",
      "answer_space": {"type": "noul"}
    },
    {
      "id": "quality",
      "prompt": "How suitable is the route?",
      "answer_space": {"type": "score", "levels": ["Poor", "Adequate", "Excellent"]}
    }
  ]
}
Files and stdin
nouli --input request.json
nouli --input request.toon
nouli --input - --input-format json < request.json

JSON and TOON accept the same question fields. Save a TOON-formatted request as request.toon; renaming a JSON file does not convert it. Stdin requires an explicit --input-format json or toon. Use a request file for structured state. Do not combine --input with inline state/questions.

A score is an expectation over indices starting at 0. On a three-level scale, 1.43 is a valid score. It is different from choosing the most likely level. Provider confidence is separate from answer probability.

Choose your output

auto shows readable text in a terminal and JSON when redirected. Set output = "text" or output = "json" in your config, or override it for a call.

Output options
nouli --input request.json --json
nouli --input request.json --format text
nouli --input request.json --format toon

Keep context across decisions

Decisions are saved by default. Name a new session, continue it, or start a separate session from earlier decisions.

Sessions
nouli --input request.json --name Planning
nouli --input request.json --session Planning
nouli --input request.json --from Planning --name Alternative
nouli --input request.json --from Planning --from Alternative --name Combined

Update the request's facts or questions before continuing. One --from starts a branch; several combine histories in a new session. The sources stay at the points you selected, so later source changes do not appear automatically. Different score scales remain distinct.

For a decision you do not want to save, use --no-session. It can also read saved context with --from, but cannot be combined with --session or --name.

Temporary decisions and inspection
nouli --input request.json --no-session
nouli --input request.json --from Planning --no-session
nouli sessions list
nouli sessions show Planning
nouli context Planning
nouli sessions export Planning --format json > planning.json

To see how a session's decisions connect, print its decision graph:

Decision graph
nouli view --session Combined
nouli view --session Combined | less -S
nouli view --session Combined --mermaid > combined.mmd

Each turn is a box containing its session, questions, available choices or rubric levels, and their probabilities. The selected choice or returned numeric result is marked with ▶ and highlighted in green and bold in a terminal. Earlier decisions appear at the top, with arrows leading to later decisions. Independent histories appear side by side, and blends appear below their sources. Shared ancestors appear once. It includes the source history captured by the selected session; later source changes and other branches stay outside the graph. Use a saved session's name or ID with --session.

[latest] marks the selected session's latest saved turns, and ╳ marks lines crossing without joining. Long questions and option descriptions wrap inside their boxes, with each turn's questions kept together. Noul results keep P(yes), and score results keep the expected value. Set NO_COLOR=1 to disable color; piped output stays plain text with the result marker. For wide graphs, pipe the output to less -S and scroll horizontally; use nouli sessions show NAME or nouli context NAME for complete details. The graph is plain text, prints once, and does not require API credentials or change saved history.

Add --mermaid to print the graph as Mermaid flowchart source instead. Paste it into a ```mermaid block in a Markdown file, and GitHub, GitLab, or another Mermaid renderer draws the boxes and arrows. Selected results are bold and marked with ▶.

Saved data lives in ~/.nouli by default. Choose another location with --store /path/to/store. If context becomes too large, older optional material may be shortened or left out of a later request. Your saved history remains available through inspection and export.

Run and resume workflows

Use a workflow file when later questions depend on earlier answers. To run your workflow, inspect its progress, or resume an unfinished run:

Workflow commands
nouli workflows run workflow.json --name Review --parallel 2
nouli workflows show RUN_ID
nouli workflows resume RUN_ID --jsonl

The example chooses a route, then asks whether to book it. Edit the facts and questions before running it.

Replace RUN_ID with the ID returned by your run. Resume reuses completed results and uses the original provider/model settings. Supply the original credential variable through your shell or the env file used when resuming. --jsonl streams progress followed by a final result.

For individual decisions, supply a stable --request-id NAME to retrieve a completed result on a repeated call. If an interrupted request needs another attempt, repeat that same call with --retry-interrupted. An interrupted provider call may have run without a saved result, so retrying can repeat it.

Troubleshooting

MessageWhat to do
providers_requiredOpen the configuration path shown in the error. Define a [providers.NAME] section using a provider example above.
provider_requiredSet default_provider to an existing provider name or pass --provider NAME.
model_requiredSet top-level default_model, pass --model MODEL_ID, or select a model in your request.
unknown_providerCheck that the selected name matches a provider defined in your config.
credential_unavailableSet the environment variable named in the error. Supply it in the shell or the selected env file and ensure it contains a valid key.
env_file_not_foundCheck the path supplied to --env-file. An explicitly selected file must exist.
env_file_unreadableCheck the env file path and read permissions.
invalid_env_fileCheck env-file assignment syntax, balanced quotes, and UTF-8 encoding.
invalid_model_budgetFor an unrecognized model or custom/local endpoint, add a supported budget under [providers.NAME.models."MODEL_ID"] or pass --context-budget TOKENS. Keep it within the model's capacity.
configuration_not_foundCheck the path supplied to --config. Nouli only scaffolds its default configuration file.
invalid_configuration_syntaxCheck TOML syntax and setting names. Keep top-level settings before provider sections.

Use nouli --help for all options and nouli workflows --help for workflow commands. A provider may refuse an individual question; a refusal is different from a connection or authentication error.
